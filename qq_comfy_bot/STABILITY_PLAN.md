# 晚风稳定性重整：阶段 1 与后续架构边界

本文件适用于 `stability-routing-and-memory-20261114` 修复分支。先保证能正确接收、回应、保存和恢复，再加入 STBridge 类的好感度、情绪、表情包、主动聊天功能。**不开发 TTS、RVC、唱歌。**

## 阶段 1 已修改（尚待本机全量验证）

1. `chat_analysis.should_split` 不再只按 240 字符分流；先参考讨论深度与简短关系/上下文信号，长度（示例配置 90）仅兜底；`0` 仍显式禁用。语义路由是第一轮规则，不应宣称覆盖所有隐含语义。
2. 当分析 API 出错，`bot.respond` 回到包含记忆元数据的完整文字契约，避免仍用 `front` 契约导致本轮记忆丢失。仍可能因接口失败无法完成回复，但不得伪造分析结果。
3. `Life.record` 强制记忆值直接出现在本轮证据中，避免“证据为真、模型提炼出的事实却是编造”的污染；暂时牺牲对改写型摘要的自动保存，未来须用带来源偏移的安全提取器恢复。
4. `Life.mood` 空差量仅读取，不修改持久状态和时间戳。
5. 移除 `len(self.tasks)<20` 对 QQ 入站消息的静默丢弃；对单条事件及接收循环的意外异常记录 traceback，避免无提示退出主 WebSocket 接收器。**这不是无限队列方案**，仍需要下一阶段给每会话与全局队列设置可观测的背压。
6. `image_director.decide` 不再把自动候选的活动描述当作用户明确索图。明确请求拥有独立来源，自动分享必须经过限额与免打扰检查。

## 阶段 2：统一调度，先实现再恢复新能力

将任务按来源和副作用分层，而非让各模块决定总体优先级：

| 层 | 类型 | 规则 |
| --- | --- | --- |
| 0 | 用户停止、取消、重置、重要状态命令 | 立即更新对应会话版本；终止尚未交付的旧任务；不误取消其他会话 |
| 1 | 用户输入的文字回复 | 优先保证可答，按会话串行，跨会话并行；返回内容不依赖 GPU |
| 2 | 用户明确授权的绘图 | 高于任何自动图片；可独立运行，不阻塞文字 |
| 3 | 用户主动打开的表情/回复附带表情 | 只在文字可交付时考虑；基于同轮情绪，不触发额外模型 |
| 4 | 自动舒缓图、搞怪图、虚拟生活图 | 经过用户免打扰、关系边界、冷却、预算、场景版本和 GPU 容量检查 |
| 5 | 主动搭话、定时分享、天气与日程预取 | 让位于用户输入；失败有冷却；不得占满接收循环和上下文构建 |

`image_director`、`image_candidates`、`initiative` 和 `bot` 不应分别执行不一致的最终授权。建议抽出 `policy_decision`：每条任务产生唯一 `request_id`、`conversation_key`、`source`、`priority`、`revision`、`reason`；任何新任务根据同一权限快照做统一准入，失败必须落日志和可查询状态。

## 阶段 3：上下文单一入口

每轮用户消息先冻结同一份 `ContextSnapshot`，包括以下隔离字段：

- `identity`：角色卡、当前场景版本（系统级真值；不可由生成回复随意改写）
- `conversation`：当前会话历史、话题、未回答问题；不同 QQ 会话严格隔离
- `user_facts`：有原文依据的长期记忆，仅关联本 QQ 用户
- `mood`：角色当下临时情绪，不作为永久用户事实
- `routine`：预存角色生活设定，不冒充已经发生的动作
- `tasks`：来自持久任务账本的事实；模型不能根据旧承诺推断任务已启动
- `relevant_lore`：按当前内容检索，不得直接写回角色卡

分析 API 和前台回复 API 读取同一 `snapshot_id` 与 `conversation_revision`。分析输出只是候选建议，不能调用 GPU、修改关系、生成不可撤回的状态；后端协调器校验来源后再决定是否暂存/提交。旧 revision 的分析结果一律作废。不得重复在各模块独立提取同一轮用户事实。

## 阶段 4：提交与故障恢复

1. 用户输入原文持久保存且幂等，和 QQ 入站 `message_id` 关联。
2. 模型返回的 `reply`、`memory_updates`、`affect`、`image_request` 先通过一个结构化边界；未知字段不进入执行。
3. 将待发回复与可能的状态变更写入 `pending_turn`。状态变更按类型区分：用户明确事实可独立验证，角色宣称的经历和关系变化必须等待相应的 QQ 发送 ACK。
4. QQ 的 ACK 明确、拒绝、未知分别记账，UNKNOWN 禁止无条件自动补发，防止重复消息。
5. 确保所有异步任务都有 deadline、取消信号、任务 ID、健康心跳与可观测的最终状态；超时不允许把队列、锁、GPU 预约永久占住。
6. 在启动时核对未完成任务；只恢复可验证的安全结果，任何可能已经发出的消息不得盲目重发。

## 阶段 5：稳定后加入 STBridge 的交互优点

优先序：先统一情绪状态和带过期时间的心情，再把好感度/熟悉程度区分；然后扩充可管理的表情图库，最后增加有免打扰、无人回应退避、每天上限的主动文字聊天。各模块共享当前轮次已经验证的情绪与关系结果，不能在后台各自反复调用模型。

## 验收门槛

以下场景必须全通过，才能合并到稳定主分支：

- 12 字的关系追问触发完整分析，普通短确认走单调用；分析超时回退不丢元数据
- 50 条密集消息不会被 GPU/后台任务数量静默吞掉；收到新消息可打断旧的未发送回复
- 私聊与群聊不能互相读取隐私；角色的虚拟日常和用户本人事实永不交叉写入
- 模型编造的记忆值即使使用了真实证据也不能保存；明确纠错仍有效
- 自动活动包含“拍照”不能越权成明确绘图；用户明确 /拍照 仍能按原流程受理
- ComfyUI 卡住、QQ 断线、模型 API 超时、重启、消息 ACK 未知时能安全恢复或明确报错
- 关键时间与状态读取不在暗中写库；所有不可逆副作用都有来源、版本和记录
- 运行全量 Python 单测、ComfyUI 假端点、NapCat 假 WebSocket、长聊及重启恢复回归；实际生产私有数据库和密钥不入库

> 当前分支只完成阶段 1 的一组低风险修复及相应回归测试源文件。没有运行 Windows 本机服务、真实 QQ、GPU 与全量单测，不能宣称整个系统已经稳定。
